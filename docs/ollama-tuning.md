# Ollama 调优（8GB 显卡）

本项目的性能上限几乎全部由显卡显存决定。这份文档记录**实测出来的**参数，
以及为什么是这些值——换机器前请重测，不要照抄。

## 必须设置的服务端环境变量

```powershell
setx OLLAMA_FLASH_ATTENTION 1
setx OLLAMA_KV_CACHE_TYPE q4_0
# 然后重启 Ollama（退出托盘程序再启动）
```

**这两个变量必须设在系统环境里，不能只设在调用方的 shell 里。**
Windows 上 `ollama app.exe` 不会继承调用方的环境 —— 在 shell 里 `export` 之后再
调用 API 是无效的，服务端读的是它自己启动时的环境。项目早期在这个坑上浪费过时间。

设置完用服务端日志确认（`%LOCALAPPDATA%\Ollama\server.log` 里的 `server config`）：

```
OLLAMA_FLASH_ATTENTION:true  OLLAMA_KV_CACHE_TYPE:q4_0
```

## 为什么需要 KV 量化

KV 缓存是「上下文」在显存里的真实形态，与文本大小无关。每 token 的开销：

```
2 (K和V) × 36 层 × 8 个 KV 头 × 128 head_dim × 2 字节(fp16) = 147,456 B ≈ 144 KB
```

**实测验证**（`ollama ps` 给的是精确字节数）：

| num_ctx | 总占用 | 与上一档的差 | 每 token |
|---|---|---|---|
| 2048 | 2.68 GB | — | — |
| 8192 | 3.61 GB | 953 MB | 162 KB |
| 16384 | 4.75 GB | 1168 MB | 149 KB |

公式预测 144 KB，实测 149~162 KB，对上。

尺度感：一段 600 字的资料 ≈ 600 token ≈ **84 MB 显存**，而这段文字本身在磁盘上
只有 1.8 KB —— **相差约 5 万倍**。

## 量化后的实测上限

**判定标准是两个模型都 100% 驻留显存** —— 不是「能不能装下」。装不下时 Ollama 会把
一部分甩到 CPU，而那是真正的性能杀手。

| num_ctx | qwen3:4b | bge-m3 | 判定 |
|---|---|---|---|
| 8192 | 3.08 GB | 0.62 GB (100%) | ✅ 量化前的天花板 |
| **10240** | 3.24 GB | 0.62 GB (100%) | ✅ ← 当前配置 |
| 11264 | 3.31 GB | **1.18 GB (22%)** | ❌ 掉到 CPU |
| 12288 | 3.39 GB | 1.18 GB (22%) | ❌ |
| 16384 | 3.69 GB | 1.18 GB (22%) | ❌ |

**量化前是 8192，量化后是 10240（+25%）。**

### 两个必须知道的测量陷阱

**① 单次扫描会给出假阳性。** 第一遍扫描时 12288 报「✅ 两个模型都在显存」，
但连续多轮测试立刻打脸：11264 和 12288 每一轮 bge-m3 都只有 22%。
**判定必须连续跑 3 轮以上**，干净状态下的偶发成功不能当结论。
（原因大概是桌面显存占用本身在波动，贴着边时成败随机。）

**② 失败时的现象是 size 变大**：`bge-m3` 从 0.62 GB **膨胀到 1.18 GB** 且只有 22%
在显存 —— 因为多留了一份 CPU 侧拷贝。**看到 size 变大就是掉到 CPU 的信号。**

**代价有多大**：bge-m3 掉到 CPU 后，单次 retrieve 从 56 ms 劣化到 **5474 ms**（100 倍）。
所以宁可保守。

### q8_0 真正的收益是余量，不只是窗口

每 token 的 KV 从 147 KB 降到 ~82 KB（降 44%，不是理论上的 50%，有对齐和额外缓冲）。
在 8192 下总占用从 4.6 GB 降到 3.70 GB，**空出约 0.9 GB**：

- bge-m3 不会被挤出去（避免 4-8 秒的重载抖动）
- 对桌面显存占用波动有容忍度（浏览器标签、其他程序）
- 窗口本身 +25%

**换机器或改了桌面占用，务必重测。** 真出问题就退回 `num-ctx: 8192`。

### q4_0：再降一档（2026-09-19 实测）

q8_0 之上再降一档到 `q4_0`，每 token 的 KV 从 **76.7 KB → 40.7 KB**（≈53%），
**两个模型同驻的容量墙从 32768 推到 49152**（同一桌面、同一天配对测得）：

| num_ctx | q8_0 | q4_0 |
|---|---|---|
| 16384 | 3.97G ✅ | 3.36G ✅ |
| 32768 | 5.25G ✅ | 4.05G ✅ |
| **49152** | **❌ 驻留 0.00G、11 tok/s** | **✅ 4.81G、100 tok/s** |
| 65536 | — | ❌ 11.6 tok/s |

工具：`tools/kv-quant-wall-probe.py`（判据与本文档一致：生成 ~100 tok/s **且** embed 延迟 30~100ms）。

**两个必须一起看的验证**（`tools/kv-quant-needle-probe.py`、`tools/digit-garble-probe.py`）：

- **32K 窗口能用**：24K 字上下文、6 个深度各埋一条事实，q4 与 q8 都是 **6/6**（含 5% 与 95% 深度）
- **数字糊化没出现**：同一个探针，q8 下 10/10 都写成「60: 600」，q4 下 0/10
  （**别读成"q4 更准"** —— 量化噪声是数值彩票，它只是没在这条上翻车）

**注意跨天不可比**：09-17 量到"q8 下 32768 崩"，今天 q8 在 32768 是好的 ——
桌面显存会挪墙。要论证档位的作用，**必须在同一天做配对**，别拿今天和上周的数比。

**当前配置仍是 `num-ctx: 16384`**，没有跟着往上抬：容量有了，但**没有仪器能把它换成收益**
（两门基准都在天花板），而解码随上下文变长会变慢（13K 上下文实测 46~50 tok/s）。

### 跑完换档位的探针，务必确认没有残留的 runner

反复换 `num_ctx` 装载/卸载（悬崖探针就是干这个的）会留下**孤儿 `llama-server` 进程**，
它们继续占着显存。症状是**下一次加载直接掉 CPU**（`ollama ps` 显示 `96%/4% CPU/GPU`），
应用侧表现为一次问答从十几秒变成十分钟，而**日志里什么错都没有**。

```powershell
(Get-Process llama-server -ErrorAction SilentlyContinue).Count   # 应为 0（没有模型加载时）
nvidia-smi --query-gpu=memory.used,memory.free --format=csv,noheader
```

2026-09-19 实测：跑完一轮档位扫描后残留 8 个进程、GPU 只剩 824 MiB 空闲；
重启 Ollama 后回到 1451 MiB 已用 / 6449 MiB 空闲。（这也说明**跨天的墙测量不可比** ——
桌面与残留进程都会挪墙。）

## 为什么不用更大的模型

| 模型 | 结论 |
|---|---|
| `qwen3:4b` | ✅ 当前在用（16384 窗口，约 100 tok/s，与 bge-m3 同驻） |
| `qwen3:8b` | ⚠️ **旧判死撤销一半：默认装载仍然不可用**。q4_0 + 8192 窗口下，**默认装载 8b 抢到 6.19G，bge-m3 被挤出**（embed 3.5s，3/3 复现）——Ollama 按**装载那一刻的空闲显存**决定往 GPU 放几层，所以同一个模型会给出 5.32G / 6.19G 两种占位，**这是看运气的**。用请求级 `num_gpu=26~30` 钉住层数后：8b 4.49~5.10G，**bge-m3 每轮都驻留（37~92ms）**，生成 27~34 tok/s（4b 是 ~100）。⇒ 路已验证，代价是窗口减半 + 速度掉到 1/3；换之前先做回答质量 A/B。工具：`tools/8b-fit-stability-probe.py` |
| `qwen3.5:9b` / `llama3.1:8b` | ❌ 更大，未重测 |

**换更大模型前先确认真实显存够不够，否则会以「模型更强」的名义大幅变慢。**

## 为什么不能靠加上下文做长对话

本地 12288 就是天花板，与选哪个模型无关 —— 卡的是 KV cache 的显存，不是模型能力
（qwen3:4b 标称原生窗口 262144，按公式要 **36 GB** KV，纯属纸面参数）。

顺带解释一个历史问题：**Ollama 默认 `num_ctx=65536`，光 KV 就要 9.0 GB**，
比整张卡还大 —— 这是早期「向量模型被反复挤出、每次切换重载 4-8 秒」的根因。
所以 `num_ctx` 必须在请求里显式传，绝不能依赖默认值。

长对话的正解是**历史索引**（旧轮次转向量按需召回）或滚动摘要，不是硬撑窗口。

## 前缀 KV 复用

Ollama **跨请求复用相同前缀的 KV**（实测）：

| | prefill |
|---|---|
| 首次（冷启动） | 819 ms |
| 第二次（前缀逐字相同） | **44 ms** |

判据要看 `prompt_eval_duration`，**不能看 `prompt_eval_count`** —— 后者报的是
提示词总长，复用了它照样报全长（这个坑踩过，探针脚本因此给过假结论）。

含义：把不变的内容放在提示词最前面，它的 KV 只在第一次付费。反过来，
**每轮都在变的内容（比如检索到的资料块）永远全额重算**。

## 上下文长度 与 速度（实测）

工具：`tools/context-limit-probe.mjs`（长度 vs 速度）、`tools/truncation-probe.mjs`（超限丢哪段）。

**关键：测前算必须让前缀唯一**，否则 Ollama 会复用上一次的 KV，测出来的不是冷启动。
第一版没这么做，数据里出现了「6198 token 花 247ms」比「5581 token 花 437ms」还快的
反物理结果 —— 长了反而更快，一眼就能看出是复用造成的。

### 冷启动：前缀唯一，全部重算（最坏情况）

| 送入字数 | 实际 token | 前算耗时 | 每千 token | 生成速度 |
|---|---|---|---|---|
| 500 | 321 | 110ms | 109.5ms | 51.5 tok/s |
| 4000 | 2473 | 691ms | 279.3ms | 41.8 tok/s |
| 8000 | 4934 | 1416ms | 287.1ms | 37.5 tok/s |
| 12000 | 7395 | 2253ms | 304.7ms | 36.6 tok/s |
| 16000 | 9859 | 3167ms | 321.2ms | 34.2 tok/s |

**边际成本约 285ms / 千 token，基本线性**（每千 token 的耗时从 275 缓慢升到 321）。
即：**前算 1 token 约 0.285ms，而生成 1 token 约 28ms —— 前算比生成快约 100 倍。**

### 热前缀：前缀与上一次相同

| 送入字数 | 冷 → 热 | 省 |
|---|---|---|
| 4000 | 688ms → 33ms | 95% |
| 8000 | 783ms → 40ms | 95% |
| 12000 | 886ms → 29ms | 97% |

把不变的内容放在提示词最前面，它的前算只在第一次付费。主题概览正是这么放的。

### 解码速度随上下文退化

51.5 → 34.2 tok/s，**慢约 1.5 倍**。原因是注意力每一步都要读整份 KV，
长度越大每步的显存带宽开销越高。这是解码的本质代价，改不了。

## 超出窗口会怎样（这条最要紧）

**不是渐进退化，是悬崖。**

| 送入 token | 系统提示 | 用户消息开头 | 中间 | 结尾 |
|---|---|---|---|---|
| 9920 | ✅ | ✅ | ✅ | ✅ |
| ~10200 | **❌ 丢了** | **❌ 丢了** | ❌ | ✅ |
| ~12300 | ❌ | ❌ | ❌ | ✅ |
| ~25000 | ❌ | ❌ | ❌ | ❌ |

- **安全上限约 9920 token**（num_ctx=10240 的 97%）
- 一旦超过，Ollama 把整个上下文**重置到 5122 token**（正好一半），
  **丢掉的是开头**，也就是系统提示词
- 实测送到 40000 字时模型连问题和结尾都没看到，**仍然正常返回了一个看起来正常的回答，不报任何错**

后果不是「回答变差」，是「回答不再受任何约束」：三段式规则、引用标注要求、
「不得编造」全部消失。**用户完全看不出来。**

所以应用层加了提示词预算（`PromptBudget` + `ragkb.rag.agent.prompt-window-tokens`），
超预算时按优先级裁：摘要 → 召回片段 → 最旧的历史 → 资料。资料最后动，它是事实依据。

> 注意 `prompt-window-tokens` 必须与 provider 的 `num-ctx` 一致 ——
> 前者决定我们打算塞多少，后者决定模型能装多少，对不上就会撞上这条悬崖。
