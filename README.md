# RAG 知识库 · Java 版

[English](README.en.md) | **简体中文**

个人 RAG 知识库的 Java 重写。与 [`D:\vs\rag-kb`（Python 版）](https://github.com/kniv001/RAG-KB/tree/python)
**并行运行、互不干扰**，两套连同一个 PostgreSQL / Redis，切换只需改 cloudflared 的转发端口。

**当前阶段**：功能完整可用。浏览器界面、Agentic RAG、联网搜索、主题树都在跑，
外网经 Cloudflare 隧道访问。

| 能力 | 说明 |
|---|---|
| 前端 | 单页聊天界面，无框架无构建；附件上传、流式渲染、公式渲染 |
| 检索 | 向量 + 关键词 + RRF 融合；agent 做规划/评估/重试 |
| 会话 | 多轮持久化；旧轮次向量召回；一行一条的摘要；轮次笔记 |
| 知识库 | 上传或联网抓取；主题树给出「覆盖了哪些方向」 |
| 加密 | 端到端（每请求一把 AES 密钥，RSA 封装）；上传也一样 |
| 认证 | 双令牌（JWT + Redis 托管的不透明 refresh） |

## 认证：双令牌

| 令牌 | 形态 | 有效期 | 存放 | 可否吊销 |
|---|---|---|---|---|
| Access | JWT(HS256) | 30 分钟 | 前端内存 | ❌ 到期自然失效 |
| Refresh | 32 字节随机串 | 30 天 | Redis + httpOnly Cookie | ✅ 登出/改密即删 |

| 接口 | 作用 |
|---|---|
| `POST /api/auth/login` | 校验密码 → 返回 access，下发 refresh Cookie |
| `POST /api/auth/refresh` | 换新 access，并**轮换** refresh |
| `POST /api/auth/logout` | 删 Redis 记录 + 清 Cookie |
| `POST /api/auth/password` | 改密并吊销该用户全部会话 |
| `GET /api/auth/me` · `GET /api/auth/config` | 当前用户 / 登录页公开参数 |

失败限速 10 次 / 15 分钟；用户名不存在时也跑一次哈希，消除时序侧信道。
401 响应体带 `expired` 标记，前端据此决定「去刷新」还是「跳登录」。

### 与 Python 版共用 users 表（重要）

两套系统连同一个库，因此密码哈希必须逐字节兼容。Python 版为绕开 bcrypt 的
72 字节上限，**先做一次 SHA-256 再把原始摘要交给 bcrypt**；Java 的
`BCryptPasswordEncoder` 是直接哈希口令字符串 —— 输入不同，同一个密码两边算出的哈希对不上。

所以实现了 [`Sha256BcryptEncoder`](rag-kb-security/src/main/java/com/kniv/ragkb/security/Sha256BcryptEncoder.java)
复刻同一方案，并必须走 `BCrypt.hashpw(byte[], salt)` 重载（原始摘要含非 UTF-8 字节，
用 String API 会被二次编码破坏）。库里的值形如 `$2b$12$...`，不加 `{bcrypt}` 前缀。

接一家新服务（DeepSeek / 通义 / Moonshot / 智谱 / 硅基流动 / OpenAI / vLLM / LM Studio）
只需在 `application.yml` 补一段配置，不用改代码。

用 JDK 自带的 `java.net.http.HttpClient`：`BodyHandlers.ofLines()` 原生支持逐行读，
做 NDJSON（Ollama）与 SSE（OpenAI 兼容）都是零依赖，不必为流式引入响应式栈。

### 跑飞保险丝：`num-predict`（默认 8192）

**2026-09-23 实测到一次跑飞**：单个请求在 Ollama 里生成到 **25756 token 还在继续**
（`slot context shift, n_keep = 4, n_discard = 8189` 反复出现 —— 越过 `num_ctx`
后在丢窗口继续生成），把显卡占住七分钟以上，**是人工杀进程才停的**。

根因：`num_predict` **从来没设过**（配置类里默认 0 = 不限制，yml 里根本没这一项），
而唯一的看门狗 `stream-idle` 是**两个 chunk 之间的空闲超时** ——
跑飞时 token 一直在流，**它永远不会触发**。从提示词到模型到传输，没有任何一层会喊停。

取值依据（15 次真实问答的生成 token）：**中位 1848、最大 4133**，那次跑飞 25756+
⇒ 取 **8192**（最大正常值的 2 倍、跑飞的 1/3），只在病态时才咬。

⚠️ **残留风险**：要保证"生成不越过上下文"需 `提示词 + num_predict ≤ num_ctx`。
实测提示词 3606~6303 ⇒ 8192+6303 < 16384 安全；但**预算允许提示词长到 12288**，
那种情况下仍会 context shift。干净做法是按 `num_ctx − 估计提示词长度` **动态**给值（**还没做**）。

### 流式与加密的冲突（设计要点）

过滤器的响应加密是「把响应整体缓存下来再加密」，而 SSE 的价值恰恰是**边生成边推** ——
两者直接冲突。所以流式路径（默认 `/**/stream`）**只解密请求，响应由控制器逐事件加密**：
过滤器把 AES 密钥放进请求属性交接给控制器，控制器在流结束时清零。

> 模式必须写成 `/**/stream` 而不是 `**/stream`：`AntPathMatcher` 按 `/` 切段，
> 请求 URI 以 `/` 开头会产生一个空段，缺前导斜杠会**静默匹配失败** ——
> 表现为「流式接口返回 application/json 且只有一个响应体」。

### ASYNC 派发与 SecurityContext

SSE 是异步请求，容器在流结束时会对同一路径再做一次 **ASYNC 派发**。
`OncePerRequestFilter` 默认跳过异步派发，所以 JWT 过滤器第二趟不执行；
而 Spring Security 6 起不再自动保存 SecurityContext —— 不显式保存的话，
异步派发会判定为未认证，表现为「流跑到最后突然 500 / Access Denied」。
解法：`RequestAttributeSecurityContextRepository` 把上下文存进**请求属性**，它会跨异步派发保留。

## 端到端加密

### 为什么做

**Cloudflare 会终止 TLS，所以 CF 能看到经它转发的全部明文。** 应用层再做一层
RSA + AES 混合加密后，链路上（含 CF）只能看到密文。

### 必须清楚的边界

> **前端 JS 本身也由 Cloudflare 分发。** 所以这层能做到「防中间设备偷看」，
> 但做不到「防中间设备使坏（替换 JS）」。要拿到完整端到端，客户端必须由自己控制
> —— 桌面端或 App。这也是后续「渲染 + 流式输出」规划的同一条路。

### 协议

| 头 / 体 | 内容 |
|---|---|
| `X-Enc-Key` | `base64( RSA-OAEP(aesKey) )`，AES 密钥由客户端**每请求新生成** |
| `X-Enc-Meta` | `base64( {"iv","d"} )`，明文 `{"ts":毫秒,"nonce":"..","token":".."}` |
| 请求体 | `{"iv","d"}`，明文即原始请求 JSON（仅方法有体时） |
| 响应体 | `{"iv","d"}`，复用同一把 AES 密钥、**换新 IV** |

**为什么令牌放在加密的 meta 头里**：若只加密请求体，`Authorization` 头仍是明文，
中间设备照样能拿到令牌直接调用 API —— 加密就白做了。头的方式对 GET/DELETE 也统一。

**为什么密钥每请求新生成**：服务端不需要存任何客户端密钥，无状态、可水平扩展，
也不怕 Redis 被读到密钥。

**防重放**：`ts` 与 `nonce` 都放在**密文内**（放头里可被篡改）；时间窗 ±5 分钟，
nonce 落 Redis（TTL 10 分钟）。

### 互操作陷阱（已解决）

Java 的 `RSA/ECB/OAEPWithSHA-256AndMGF1Padding` **默认用 SHA-1 做 MGF1**，
而浏览器 WebCrypto 的 `RSA-OAEP(hash=SHA-256)` 摘要与 MGF1 **都用 SHA-256**。
不对齐就永远解不开。代码里显式构造了 `OAEPParameterSpec("SHA-256","MGF1",SHA256,...)`。

AES-GCM 的密文布局两边一致（ciphertext‖tag），无需转换。

### 文件上传的加密（已解决）

multipart 的分片边界、头字段、文件名全是明文，Cloudflare 终止 TLS 后能完整还原出
文件与令牌 —— 而那正是这层加密要防的东西。所以**不改造 multipart，另开了一条路径**：

```
POST /api/docs/upload-encrypted
Content-Type: application/octet-stream
X-Enc-Key    RSA-OAEP 包裹的 AES-256 密钥
X-Enc-Meta   加密的 {ts, nonce, token, iv, name, size}
体           文件密文本身（ciphertext‖tag）
```

**文件名与文件 IV 放在加密的元信息里**，不放请求头 —— 放头里等于没加密。

两个实现要点：

- **体不进内存**。整个读进来解密的话，一个 50MB 文件要占 100MB 堆。
  过滤器只把密钥与元信息交接给控制器（`ATTR_AES_KEY` / `ATTR_META`），
  体原样透传，控制器边读边解密边落盘，峰值只有一个 64KB 缓冲。
- **先写 `.part` 临时文件，认证标签校验通过后才改名就位**。否则一个标签不对的
  请求会在磁盘上留下半截文件，而它看起来和正常文件一模一样。
  这里刻意不用 `CipherInputStream` —— 它在 AEAD 上有历史坑（JDK-8012631），
  标签失败时可能吞掉异常、静默截断。改成自己 update/doFinal 循环，标签不对
  会在 `doFinal` 上明确抛出。

老的 multipart 接口保留未动，避免破坏可能存在的旧客户端。

## Agentic RAG

规划 → 检索 → 评估 →（不足则换查询再来）→ 生成。agent 只是控制流，
**事实来源始终只有检索到的资料** —— 三条硬约束保证这一点：可用动作只有「检索」
（不联网、不写文件）；资料不足时如实说不知道；回答逐条标注来源编号。

**规划与评估强制结构化输出**（关思考 + 语法约束 JSON）。这是本项目收益最大的一处优化：

| | plan | assess |
|---|---|---|
| 关闭 | 51.5 秒 | 31.4 秒 |
| 开启 | **0.94 秒** | **1.6 秒** |

根因是模型为吐一个三行 JSON 先生成了 4561 个 token 的推理。**两个开关必须同时给**：
只关思考，推理会从 `thinking` 通道漏进 `content` 通道把 JSON 冲碎；
只给约束，模型照样先想完再输出。

**回答三段式**（`ANSWER_SYSTEM`）：有资料就严格按资料答；没资料也不要甩一句
「没有」了事，而是先声明知识库没有、再用通用知识作答并标注来源边界；
闲聊与身份问题不套知识库约束。标注写得硬，是因为它是这套系统**唯一的信任边界**
—— 用户必须一眼分得清哪句来自自己的资料、哪句是模型的通用知识。

### 类型判定改由代码给（`contract-in-code`，默认开）

三段式的第一步是"判断问题属于哪一类"（有资料/没资料/与库无关），而模型**每道题都要重推一遍**。
实测：思考里与输出契约有关的句子占 **20%**（闲聊题高达 **49%**）。

现在这件事**由代码判**：对**每一块**资料读「是 / 否」两个 token 的概率
（`raw:true` + `logprobs`，**不生成** —— 生成式会掉进「恒选一侧」的退化解），
单块过线即【乙】、一块都不过即【丙】。逐题开销 ~0.2~1.7 秒，
**比它取代掉的那步评估（~1.8 秒）还便宜**。

实测：**TTFT 中位 4.0 → 2.6 秒**、总耗时 −23%、思考 −20~25%；
质量不掉，且**标签泄漏 7/105 → 0/105**（提示词里那句"不要复述类别"堵住了它）。

⚠️ **信号不可用时不再猜**：拿不到「是/否」就退回原提示词 ——
否则会静默地把每一题都判成【丙】、答得出来的问题答「知识库中没有」。

### 引用规范化：模型尽管写，后端收敛（`CiteFix`）

**问题**：只要**注入的单位比"块"更细**，模型就自发按句子粒度引用 ——
2026-09-23 连着两次实测到（给了地址那轮写 `[1.7]`；**没给地址**的分层注入那轮
自己编 `[4.3]`、`[2.11]`），而那些引用**逐条核对全是对的**。
可判据的正则 `\[(\d{1,2})\]` 与前端渲染都只认 `[n]` ⇒ **好答案被判成"缺引用"**
（grounded 6/6 → 1/6）。

**做法**：不跟模型对抗、也不改判据迁就它，**在出口收敛一次**。
`CiteFix` 在流式正文里见 `[`/`⟨` 就攒着（引用可能跨 token），凑够再判：

- 句子级引用 ⇒ 收敛成 `[n]`，**句号与在正文里的偏移另记**
- 不是引用（markdown 链接、正文方括号）⇒ 原样放出
- **攒超过 12 个字还没收口也原样放** —— 宁可格式差，不能吞字

**实时与缓存回放两条路都要过**：缓存里存的是模型原文，不回放就会出现
「第一次看是 `[4]`、命中缓存却变回 `[4.3]`」。

句子号不丢：随 `stats` 事件发 `cites=4.3@123,…`（`@` 后是正文偏移），
判据用它判"引的那一句对不对"——**前端不渲染句级，契约仍然是 `[n]`**。

## 文档入库

两条入口，**文本提取走的是两条不同的路**：

| 入口 | 支持 | 提取方式 |
|---|---|---|
| 上传 | `.txt` `.md` `.markdown` `.pdf` `.docx` `.csv` `.json` `.html` `.htm` | 按后缀分派：PDF→PDFBox、DOCX→POI、CSV→拼成「表头 \| 值」的行、JSON 原样、**HTML→`HtmlToText`**、未知后缀按纯文本处理（不报错 —— `.log` `.conf` 这类不该被拦住）。PDFBox 与 POI 都是重量级依赖，**只在真遇到对应格式时才触发类加载** |
| 联网抓取 | 任意网页 | 先挑 `<main>`，再走**同一份** `HtmlToText`（上传与抓取共用一个实现）：h1–h6 → `#`…`######`、列表 → `- `、**表格线性化**（列头绑进每一行）、代码块围栏保留 |

**抓取为什么改成输出 Markdown**（2026-09-17 落地）：原先用 `main.text()` 把 DOM 拍平，
标题层级当场就没了 —— 41 篇已入库文档里只数出 **64 个标题行**，而且大多是入库时自己加的那个。
后果不只是"不好看"：后来想**从语料里反推结构**的三条路（模型定章 / 模型归并 / k-means 归并）
全部不通，因为**结构在提取环节就已经丢了** —— 正解是提取时白拿，不是事后补。

效果：同一篇博客重抓，**7161 字带 59 个标题**。只对新抓的文档生效，旧文档仍是拍平的。

> **不对称已消除**（2026-09-20）：上传的 `.html` 原先走的是正则剥标签
> （`<[^>]+>` → 空格），于是**导航与页脚的文字全留下、标题层级全丢、表格被拍平成
> "列义只由位置隐含"**。用一张合成靶子页走真实入库路径实测后，两条路统一到
> `HtmlToText`（`service/parse/HtmlToText.java`），修法全是机械的、不需要模型：
>
> - 按标签剥 `nav/footer/aside/form/…` 以及 `role=navigation|banner|contentinfo`
> - 标题输出 `#` 前缀 —— 这是「标题路径随块携带」（**免费的** contextual embedding）的前提
> - **表格线性化**：`- 方案：计数器；突发流量：不支持；实现复杂度：低；典型场景：内部接口兜底`
>   —— 表格的语义在**表头↔单元格的关系**里，扁平化恰好丢掉的就是那个关系；
>   绑进每一行之后，块**切在哪儿都不丢列义**
>
> 验收：`node tools/ingest-shape-probe.mjs`（那三个靶子现在全清）。

**索引管线**：解析 → 切分（下一节）→ **语境行** → 向量化 → 入库，全链路带缓存 ——
解析按「**文件内容哈希 + `DocumentParser.VERSION`**」缓存（换解析器要加版本，否则同一份文件仍命中旧解析）、语境行按「文档名 + 块文本」哈希缓存、向量按「文本 + 模型哈希」缓存
（所以重建索引几乎瞬间完成）。三层缓存的键都含所有影响结果的参数，不会返回陈旧数据。

**语境行**（`ChunkContextService`）：入库时给每块生成一句「**这段能回答什么问题**」，
**只拼进嵌入文本、永不进提示词** —— 回答里展示与引用的仍是原文（逐字可追溯是这套系统
唯一的信任边界，不能被索引层的改写污染）。

为什么需要它：2026-09-18 的难题集量到一个真失败 —— 问句用**症状词**（「怎么让服务固定
在同一台机器上」），文档用**机制词**（「节点亲和性」「调度」），两者在向量空间里够不着：
那条的靶子排在 **rank 50**，加宽召回也没用（要提到 50 才行）。加上语境行后靶子回到
**rank 28**，难题 **13/14 → 14/14**。

两处措辞是实验定的，**不能改**：问「**能回答什么**」而不是「讲了什么」—— 后者只会复述
文档术语，精度上去了但硬失败没救；必须**禁止元信息**（「本文由某某撰写」「抓取时间」
那类实测占 9%，对检索零价值还占索引位）。免费的办法试过：只把文档标题前置**完全没用**
（标题带的还是机制词）。退化的输出（只写省略号或空话）当作没生成，索引照建。

代价：入库时每块 1 次 4b 调用（661 块约 20 分钟，后台跑）；**查询侧零开销**。

**入库不会自动重建主题树** —— 语料变了要手动触发（`POST /api/tree/build`，或改语料后跑
`tools/tree-rebuild.mjs`），否则概览里报的还是旧语料的簇与块数。

## 分块

600 字目标 / 80 字重叠，**边界按句子对齐**，不按字符位置硬切。

超长段落先切成句子再打包，相邻块之间带**整句级别**的重叠；只有单句本身超过 600 字
（代码块、无标点长串）才退回字符切。

为什么较这个真：**「从句子中间开始」的块占比实测 75% → 13%**（六篇文档对照，四篇降到 0）。
半句开头的块指代无从解析、语义不完整，既是检索的噪声，也是抽取类任务失败的直接原因 ——
同一段按句子边界对齐后，模型三次抽取都正常且条数完全一致（22/22/22），硬切那版三次里空过一次。

**换行不能一律当边界**：这个语料是网页抓来的，75% 的行是硬折行（一句话折成好几行）。
判据是「换行两侧只要有一行不含中文就当边界」—— 代码/输出行不含中文（抽样占 75%），
天然是独立单位；中文散文即使折行，两侧都含中文就不切。

> 这一版边界规则与 Python 版**不同**（Python 版仍是字符硬切）。两套共用一个库，
> 切分口径不一致会让同一篇文档在两边的检索结果对不上。

## 上下文怎么花

这块是本项目做得最细的地方，每个数都是测出来的（详见 [docs/ollama-tuning.md](docs/ollama-tuning.md)）。

**窗口 16384 token。** 超限不是渐进退化，是**悬崖**：Ollama 把整个上下文重置并
**丢掉开头** —— 也就是系统提示词。后果不是「回答变差」，是「回答不再受任何约束」，
而模型照常返回看起来正常的回答、不报任何错。所以应用层有 `PromptBudget` 按优先级裁：
**最旧的历史 → 召回片段 → 资料**（资料最后动，它是事实依据）。

> **摘要与召回片段共进退。** 摘要原先排第一个丢，2026-09-18 改了 —— 召回片段是
> 原文/笔记，**没有「谁更新」的机制**，可能带回已被改掉的旧值；而摘要正是写着当前值的
> 那一层。实测（`tools/stale-recall-probe.py`）：只召回旧片段而无摘要时 **3/3 端出陈旧值**，
> 有摘要时 **3/3 救回**。代价约 400 token（摘要 12 条 × ≤40 字）。

**实测一次问答 2.6K~6.1K token**（窗口的 16%~37%），固定部分约 1100：
系统提示 530 + 主题概览 440 + 问题。其余是资料（最多 24 段）与最近历史（最多 16 条）。

**四层，可靠性递减**：

| 层 | 内容 | 怎么来的 |
|---|---|---|
| 最近窗口 | 原文全文 | 直接取，无检索参与 |
| 更早轮次 | 向量召回的片段 | 见下面的「查询侧顺序」 |
| 摘要 | **一行一条，每条写「曾经 → 现在」** | 攒 6 条消息合并一次 |
| **长期记忆** | **跨会话**的持久事实（偏好、约定、已定下来的决定） | 从摘要产出吸收，见下 |

### 长期记忆（跨会话）

会话摘要**按会话隔离** —— 这次对话里说定的约定，换个会话就没了。
`memory_items` 表补上这一层：一行一条（同一个主题只留一行），形状沿用摘要那一套
（`主题：曾经 → 现在`），所以摘要那边的机械件（解析 / 着落判据 / 覆盖边 / 只增不删）原样可用。

**合并是纯机械的，不请模型** —— 会话摘要那边的合并要模型，因为它面对**原始对话**；
而这里面对的是**已经提纯过的一行一条**，判断只剩两件：
① 是不是同一个主题 ② 值变了吗。两件都不需要语义理解 ⇒ 确定性、不花时间、
也不会引入模型那类"把旧列表原样抄回来"的退化解。

**它必须进缓存键** —— 记忆变了答案就可能变；不进键的症状是"记忆明明更新了、
回答却还是旧的"，而且因为缓存命中不报错，**看起来像记忆没生效**。

**摘要怎么写——每一条都是实测定的**（`tools/summary-*.py`、`tools/supersede-probe.py`、
`tools/digit-survive-probe.py`）：

- **一行一条、每条写「曾经 → 现在」**。关键不是箭头，是**形状本身是完整性约束**：
  强制「两边都要写」，就把「没有变化的事实」也逼成显式的 `— → 现状`。
  早先的自由形式会让模型把不变的事实静默丢掉 —— 连跑三次，用户偏好那条丢了两次。
- **合并后条目数不该少于原来**。合并是**双模态**的：同一份输入（原有 8 条 + 同一段新对话）
  连发五次，事实存活数是 `[7, 7, 2, 8, 2]` —— 塌陷时**一次丢 6 条**，丢的全是
  「`— → 现状`」那批。所以少于原有就重试，最多三次取条目最多的那版（健康时只发一次）。
- **只增不删**：三次重试都没着落的旧条目**原样补回**。把着落判据从"评分"改成"补丁"，
  零额外调用。实测末轮种子存活 4.5/8 → **8/8**。**但它只在短列表上救命** ——
  2026-09-20 量出：列表到 18 条时模型**根本不丢**（`missing=0`），补回一次也没触发；
  代价换了个方向（见下条）。
- **覆盖边也由代码补，不问模型**。旧值被推翻时模型写的是 `分块粒度：— → 450` ——
  **旧值一律被丢掉**（12/12），提示词里明写规则也照旧 12/12。
  这是**纯字符串操作**（上一条的右值就是这一条的左值），补后 **12/12 落进「✅覆盖」**。
  顺序要紧：补边要放在只增不删**之前**，否则同一条既补回又补边，列表里会并存两条。
- **冻结检测**：输出与输入**逐字相同** ⇒ 本轮新信息一条都没落地。
  它是"丢事实"的**反方向**退化（长列表下 5 轮里有 2 轮「新信息落地 0/2」而条目数一条不差），
  只增不删治不了，原来也没有任何判据看得见。已知边界：只抓得住**完全冻结**。
- **数字要机械校验**。本机 4b 模型会往数字中间插冒号，而且**值特异、确定性、提示词治不了**：
  2026-09-20 实测 q4 KV 下 `24576` **30/30** 被写成 `2:4576`，而同一输入里其余五个数字
  （`10240`/`16384`/`450`/`1024`/`20`）**各 30/30 全对**。糊法不止一种 ——
  既有「末位被吃」（`600 → 60:`），也有「首位之后插冒号」（`24576 → 2:4576`）。
  合并后检查「摘要里的数字能否在输入里找到」，找不到就 `warn`（只记日志，不改内容）：
  **判据抓得到，自动修复没启用**（现有修复规则是按"末位"形态验的，不对症）。

**查询侧顺序是关键**：召回必须发生在**规划之后**。规划器把「那它呢」改写成了
自包含的查询，用那个当检索键才召得回定义「它」的那一轮；用用户原话当键的话，
键就是「那它呢」四个字 —— 而那一轮的文本里根本没有「它」。
规划本身用不到召回片段：它有最近 16 条原文和滚动摘要。

### 分层注入：块先框范围，块内挑句（`sent-window`，默认关）

**为什么**：实测一次问答 **86% 的时间在 decode，其中 81% 的 token 是思考**，
而思考里**中位 38% 的字是在复述已经在提示词里的资料**。
"禁止复述"那条提示词单独试过、**不通**（思考反而变长，符号检验 p=0.007）——
**只禁止不给替代**时，模型只会换个方式做同一件事。
所以换成"少给"：**块召回之后，只在那些块里按问题挑句，只装那几句**。

**句子级索引**（`sentences` 表，661 块 → 6003 句）：

- 切分是**独立的一份**（`tools/sentence_split.py`）：代码围栏整块不切、表格按行、
  标题自成一句；**每句带字符区间，且必须能逐字还原原文**（入库前逐句核，一条不符整批拒收）
- 每行带**语料戳**（按位置对齐的索引会随重建静默错位）
- 重建是一条命令：`python tools/build-sentences.py`（建表 → 算向量 → 灌库，113 秒）

**实测（21 题配对）**：

| | 整块注入 | 分层注入 top-20 |
|---|---|---|
| **装入 token** | 4894 | **2712（−45%）** |
| prefill | 1.3s | 0.7s |
| TTFT | | **−0.47s** |
| 总耗时 | | **−1.1s（没变长）** |
| 思考字数 | | 0.99（没变） |
| 答案质量 | 20/21 | **20/21** |

**"少给内容"会不会伤质量**——这条有独立测量：**答案只覆盖被引用块内容的
14%（中位）、31%（90 百分位）**（438 个样本）⇒ 保留三成，覆盖九成题目的需要。

⚠️ **`num_predict` 是另一件事，别混**：`generation-reserve-tokens` 是**提示词预算**的预留，
不是生成上限。生成上限见下面「跑飞保险丝」。

**轮次笔记**：窗口之外的轮次会被改写成自包含的笔记，**索引的是笔记而不是原文**。
单条 message 不是好的检索单元 —— 用户那句常带指代、助手那句常脱离问题、
两边都夹着「根据参考资料[1]」这类包装。改写交给**对话模型**，不是向量模型
（后者只负责把改好的笔记变成向量）。

## GPU 调度

本机只有一块 GPU，Ollama 只有一个推理槽（`OLLAMA_NUM_PARALLEL=1`），请求 FIFO 排队。
所以后台任务会**等满**地拖慢用户：

| 后台任务耗时 | 用户请求耗时 |
|---|---|
| 1314ms | 1164ms |
| 3091ms | 3095ms |

用户请求自己只要 192ms，其余全在等槽（旁证：用户的 prefill 始终稳定在 36~39ms，
如果在算这里也会涨）。

`GpuGate` 让后台任务避让：没有用户请求在跑、且静默 20 秒，才允许开始；
等超过 300 秒就放弃本次（后台任务都是增量的，下次还会再来）。

**以后每加一个后台任务，先用 `tools/gpu-contention-probe.mjs` 量一遍。**

## 联网搜索

搜到 → 抓取 → **入库成为文档**，而不是让 agent 直接联网找答案。

后者会破坏那条硬约束：网页内容没进过库、没被审过、也不知道出处，
而用户完全看不出来。变成文档之后，它跟用户自己上传的文件走同一条路 ——
一样被切分、向量化、留下出处，所以「回答里的每一句都有出处」这条性质在联网之后依然成立。

**抓取时保留原文的结构**（2026-09-17 改）。原先用 jsoup 的 `main.text()` 取正文，
那会把整棵 DOM **拍平成一串文本** —— 标题、段落、列表、代码块的结构全在这一步丢掉。
代价是可量化的：41 篇已入库文档合计只剩 64 个标题行，而其中绝大多数是抓取时自己加的那行标题，
于是「这篇文档讲了哪几块」在库里无从恢复。

现在改成遍历 DOM 输出 Markdown：标题 → `#`~`######`、段落 → 空行分隔、列表 → `- `、
表格 → `| `、`<pre>` → 围栏原样保留。实测同一站点新抓的两篇：一篇 7161 字里 **59 个标题**、
147 个段落，层级完整（`## 一、持久化的作用` / `### 1. 什么是持久化`）。

> 已知限制：用 JS 高亮器（hljs / prism）渲染的代码块是 `<div>` 而非 `<pre>`，
> 提取时不认，那部分**文字不丢但结构拿不到**。已入库的文档也补不回来 —— 结构只能在抓取时拿到。

**后端选择是实测筛的**（校园网，查「三层缓存架构」）：

| 后端 | 结果 |
|---|---|
| Bing | ❌ 把「三层」拆成单字「三」返回汉字百科页（加 mkt、换 cn.bing.com 都一样） |
| 搜狗 | ✅ 结果最准，但链接是解不出目标地址的 JS 跳转，入库拿不到出处 |
| **360** | ✅ 结果准，真实网址直接写在 `data-mdurl` 属性里 |
| 百度 / DuckDuckGo / Brave / Jina / 维基 | ❌ 反爬页或连不上 |

默认 `so360 → bing` 按顺序试。**抓取有 SSRF 防护** —— 本机 Redis 监听在
`0.0.0.0:6379`，所以每次抓取前逐个检查 DNS 解析出的**全部**地址
（只查第一个的话，一个同时解析到公网与内网的域名就能绕过）。

**默认关闭**（`KB_WEB_ENABLED=true` 才开）：这个功能会让服务端主动向外发起请求，
与「只监听本机」的默认姿态不同，应当由用户明确打开。

## 主题树

把全部块聚成若干主题簇，每簇一句概括。解决的是「语料一大，扁平的 top-k 就看不出全局」
—— 检索不到时只能回「知识库中没有」，而说不出「没有 X，但有 Y 和 Z 两个方向」。

聚类用 k-means++（固定随机种子，否则同样语料每次重建会得到不同分簇），
模型只在最后一步给每簇起名概括。只做两层不做深树：深树的收益来自逐层收窄，
而每下降一层都要付 KV，在 16384 的预算下不划算。

语料重建后 **661 条里 438 条静默错位**，让所有指标一起变低，看起来像"这条路本来就不行"。

现在：**靶子锚内容不锚位置**（题目集在 `tools/cases/*.json`，语料重建后自动重解析，
不用再改题目）；缓存在**语料戳**上对齐；**每个数字都带尺子名与语料戳**。

| 门 | 题 | 基线（k=8 / k=12 / k=24） |
|---|---|---|
| `single-hop-15` | 15 | 100% |
| `hard-query-15` | 15 | 87% / 93% |
| `multihop-25` | 25 | **56% / 68% / 84%**（篇内多跳） |
| `xdoc-8` | 8 | 75% / 100%（**跨文档多跳**，k=24 饱和） |
| `selfretrieval-23` | 23 | 排第一 43%、进 top-10 83% |
| `segmentation-10` | 10 窗口 | WindowDiff —— 线上分块 **0.77**、指认式 **0.32**（越小越好） |
| `multihop-127` | 127 | 84%（扩题版，见下） |

**另外三把尺子**（2026-09-23 加，各量一件与主流程正交的事）：

```powershell
python tools\sent-recall.py multihop-127      # 句子级召回：三个口径（全中 / 块级触达 / 精度）+ 分层臂
python tools\think-structure-read.py <运行目录>  # 思考的结构：复述问句/复述资料/重复自己/组织推理
python tools\think-structure-eval.py answer-quality qwen3:4b <臂A> <臂B>  # 上面那把在 A/B 落盘上跑
python tools\decode-split.mjs 那支……见 tools\decode-split-probe.mjs     # 通道×时间、速率五等分、对账
```

- **句子召回**：结论是**无互补、同预算更差**（同 ~6300 字预算下块臂 89% vs 句臂 71%；
  "只有句子臂中"**0 道**）。唯一亮点是小预算很省（top-20 = 1437 字触达 98% 的靶子块）。
- **思考结构**：中位 **38%** 的字是复述已在提示词里的资料、**19%** 是重复自己，
  且**复述资料集中在前 1/3、重复自己集中在后 1/3**。

### ⚠️ 做 A/B 前必须知道的三件事

1. **单次不可判**。同一配置重跑，逐题**思考字数比 0.37~2.90**、总耗时摆动 **−25s~+18s**。
   判据只能是**配对 + 符号检验**，且要 repeat。
2. **零假设不是 50%**。每次 A/B 都该配一对 **A/A 对照**（同配置、背靠背、清缓存）来量当次的
   零假设 —— 实测同场次是 **0.48（没有顺序偏置）**，而**隔 10 小时**的那一对是 0.81
   （跨小时的外加漂移）⇒ **跨小时的两次运行不能当同配置对照用**。
3. **看占比会看反**。"复述资料占比"降了（12%→8%）而**绝对字数只降 14%、总量反而 +29%** ——
   **占比 / 绝对量 / 总量三个口径要一起看**。

**平台会记 token 了**（2026-09-23 加）：每题存 `promptTokens / evalTokens / prefill / decode / tokPerSec`，
判分报告单列一段。**缓存命中时没有 stats** ⇒ 顺带成了"这题真跑了没有"的机械标记。

### 扩题流水线（`tools/cases/_spec/*.json`）

写题**只碰数据、不碰代码** —— 规格是一份 `{doc, prefix, cases:[[序号,[块号...],"问句"]]}`，
`build_spec.py` 生成题目集、`merge_cases.py` 合并（**强制换新名字**：新内容一律新名字，
否则历史数字会失去可比性而看不出来）。

⚠️ **一条要读的账**：`multihop-127` 的 127 题里，**只有 9 道关乎「索引该不该带 ctx」这个决定**。
判据「三档里只要有一档不同就算会翻」**口径太宽** —— 它把"ctx 单独做索引不够用"
（早就定论的结论）也算进来了。**判据要盯着决定，不是盯着"有没有差异"。**

### 运行记录器（`tools/run.py`）

```powershell
python tools\run.py <名字> -- <命令...>   # Python/Node/PS 都能包
python tools\run.py ls                    # 回溯跑过什么
```

完整 stdout+stderr 落 `tools/_runs/<名字>/<时间戳>/run.log`（**逐行 flush**，崩了堆栈也完整），
`meta.json` 记**参数 / 两个仓库的提交 / 语料戳 / `KB_*` 开关 / 退出码**。
探针想留完整产物（日志里通常只打 `思考[:120]` 那种节选）用 `from _artifact import save`。

单条尺子：`python tools\ruler.py run multihop-25 --k 8,12,24 --cap same --source raw`
（`--k` 每条查询取几个、`--cap` 装几个名额、`--cap same` 取 k 看 k、`--source raw|planner` 用哪批查询、
`--thresh` 距离门槛、`--mmr cos:0.90` 冗余过滤、`--repeat 3` 重复、`--pair` 配对比较给符号检验）。
分段：`python tools\ruler.py seg`（自检）、`python tools\ruler.py seg --all`（评所有候选分段）。

**模型测评**（`tools/eval.py`，与上面的**管线尺子分开**）。分工按「什么变了要重跑」划：
管线尺子量**语料与管线**（检索排第几、分段准不准），报告带**语料戳**；
这里量**模型本身**（分类判断、引用纪律、诚实性、速度），报告带**模型名**。

```powershell
python tools\eval.py ls                                    # 有哪些基准
python tools\eval.py run answer-quality --model qwen3:4b    # 采集 + 判分
python tools\eval.py score answer-quality --model qwen3:4b  # **只判分**（改判据不用重跑模型）
python tools\eval.py speed   --model qwen3:4b --n 5        # 速度维度（分阶段耗时）
python tools\eval.py compare answer-quality qwen3:4b qwen3:8b
```

**这个平台量两个维度，换一个模型两个都能量**：质量（`run` / `score`）与速度（`speed`）。
**速度的分层（qwen3:4b，q4 KV）** —— `ChatStats` 接住了 Ollama 末帧里原本被丢掉的计时：

| 层 | 数 |
|---|---|
| 规划 / 检索 / 评估 | 0.9 / 0.1 / 1.8s |
| **prefill** | 1.1~1.9s　装机 **4139~7163 token** ⇒ **~3850 token/秒**（并行，随装入量涨） |
| **decode** | 19.6~43s ⇒ **~77 token/秒**（串行，随生成长度涨） |

**瓶颈全在 decode，而 decode 里 79~87% 的 token 是「思考」**
（样本一：正文 322 字 ≈ 198 token，思考 2093 字 ≈ 1286 token）。
思考走独立通道、前端折叠展示，但**与正文在同一条 decode 流里串行** —— 想多久就多等多久。

⇒ **提速的唯一大杠杆是「少想」，不是「少写」**（早先按总数得出的"回答长度是唯一杠杆"已作废）。
回答路径的 `think` **不能简单关掉**（实测 `think:false` 是净亏：推理会转进正文污染输出）。

首个基准 **`answer-quality`**（15 题）判的就是 `ANSWER_SYSTEM` 的那三段契约，
**全用机械判据、不请裁判模型**（裁判本身不可靠时它给的分没有意义 —— 换模型当第二标注者
同意率只有 53%）：

| 题型 | 题 | 通过条件 |
|---|---|---|
| `grounded`（【乙】有资料） | 6 | 有引用 + 编号有效 + **数字有据** + 无标签泄漏 |
| `ungrounded`（【丙】没资料） | 6 | 声明了没有 + 标注了通用知识 + 无标签泄漏 |
| `chitchat`（【甲】无关） | 3 | **没误报「知识库没有」** + 无标签泄漏 |

负样本核过**主题词在同一块里凑不齐**（不能只看单词出现次数 —— 「事务」出现 191 次全是 MySQL 的）。
判据里 `None` 表示**不适用**（如没有数字的题上「数字有据」），要跳过，不是失败。

**入库形状体检**（改解析器后跑；自带 `--keep` 可留档，默认**跑完自己删探针文档**）：

```powershell
node tools\ingest-shape-probe.mjs      # 一张带 nav/表格/标题/代码的 HTML 走真实入库路径
```

> **改解析器后必须清 `cache_parses`**（或把 `DocumentParser.VERSION` 加一）。
> 解析结果按「文件内容哈希 + 解析器版本」缓存在**库里**，跨重启也在 ——
> 只按内容哈希的话，换了解析器重新索引**仍会拿到旧解析**（2026-09-20 踩过：
> 新代码确实在运行的 jar 里，入库形状却是旧的，查了半天才发现是缓存命中）。
> 语境行那条缓存键里含**块文本**，块文本一变键就变，所以它本来就对。

**长上下文体检**（改动 KV 量化档位 / 窗口 / 模型后跑，基线 6/6）：

```powershell
python tools\kv-quant-needle-probe.py q4   # 24K 字上下文里 6 个深度埋事实，q4 与 q8 都该 6/6
```

埋的是**语料里不存在**的代号与值，所以它测的不是"检索得到"而是"读得到"——
两门检索基准都在天花板，只有这条能发现"窗口装得下但读不出来"。

**难题集是这套里最该跑的**：自带词问法（「G1 垃圾回收器是怎么工作的？」）里
问题本身就带着文档的词，15/15 是必然的 —— **它测不出任何检索改进**。
换成真人会问的样子（「怎么能让某个服务总是跑在同一台机器上？」）之后才有区分度，
2026-09-18 就是靠它量出"问症状、文档讲机制"这类失败（靶子排在 rank 50），
也靠它验证了语境行的效果（13/14 → 14/14）。

一条不参与计分：**「加机器的时候为什么缓存会大面积失效？」** —— 语料里那两篇
一致性哈希文档 0 块提"扩容"、4/6 块讲"宕机"，**问的是另一个方向的场景，库里没有**。
留着它是因为它测的是**另一种能力**：语料没覆盖时，回答该老老实实说"知识库没有"，
而不是硬凑一次检索。**别把它和检索失败混在一起计分。**

### 关于「断言模型行为」的测试

`tree-test` 和 `answer-style` 里有几条断言测的是**模型输出**（回答里有没有提到主题名、
有没有「知识库中没有」的措辞）。这类断言天然不确定 —— 实测失败率约三成。

**对策是重试，不是放宽判据**：不是被测对象出错，是测试方法不对。
重试前必须清回答缓存，否则第二次拿到的还是上一次的答案。

还有一类是**测试自己过期**：知识库会长大，凡假设「知识库没有 X」的用例都是定时炸弹
（踩过三次）。现在一律用虚构话题，并在注释里写明原因。

前两个用 Node 的 `crypto` 模块实现，其 RSA-OAEP(SHA-256) 语义与浏览器 WebCrypto
**完全一致**，等于提前验证了浏览器端能不能对上。

`crypto-browser-path-test.mjs` 更进一步：它把 `app.js` 里加密层的**源码原文**按标记
切出来、在 Node 里执行（Node 20+ 的 `crypto.subtle` 就是浏览器那套 WebCrypto）。
验的是将要在浏览器里跑的那段代码本身，而不是它的副本 —— 这样才能排掉
「Node 能通、浏览器不通」这类隐患（OAEP 的 hash、GCM 的标签位置、密钥导出格式，
任一处不匹配的表现都是整站白屏）。

`frontend-e2e-cdp.mjs` 用 CDP 驱动无头 Edge，走真实加密登录、发问、附件上传，
并捕获 console 报错与异常栈。**断言一律看计算样式而不是 `element.hidden`** ——
属性为 true 但 CSS 里写了 `display` 的元素照样显示，第一版就是查了属性，
把「登录成功但遮罩不消失」放了过去。

## 已知边界

- **框架级错误响应为明文**：404/405/500 由 Spring 的错误分发产生，绕过了响应包装器。
  只含状态码与路径，无业务数据。
- **上传大小受请求体上限约束**：加密上传是单请求整体传输，没有分片，
  上限受 Cloudflare 100MB 与原站记录数限制。当前配置 50MB。
- **本地上下文上限：配置写的是 16384，实测还能更高**。2026-09-17 重测（判据：生成全速
  **且** 向量调用延迟 30~100ms 而非数千毫秒）：

  | num_ctx | 生成 tok/s（三轮） |
  |---|---|
  | 24576 | 91.8 / 104.8 / 103.8 |
  | 28672 | 91.5 / 102.5 / 102.0 |
  | 32768 | 95.7 → **10.4 / 10.2** |

  两个模型同时驻留时可用到 **24576~28672**，32768 才崩。崩的机制不是「层被甩到 CPU」
  （`ollama ps` 仍报 100% 驻留），而是显存容量墙。**墙的位置随桌面显存占用浮动** ——
  第一轮扫描曾据此得出过「32768 掉到 9 tok/s」的错结论（那次桌面多占了 0.35G），
  所以换机器或改桌面占用务必重测（`tools/joint-ceiling-v2-probe.py`）。

  配置停在 **16384**（2026-09-17 从 10240 提上来，与 `provider.local.num-ctx` 必须一致）：
  再往上到 24576 会让整卡余量只剩 552MiB，而长对话的正解是历史索引与摘要，不是硬撑窗口。
- **单会话内检索依赖指代解析**：规划器用最近 16 条原文与摘要解析指代，
  所以指代对象若在很久以前且摘要没覆盖到，仍会召不回。
